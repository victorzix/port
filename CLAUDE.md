# Project rules

- **Commit authorship.** Never add `Co-Authored-By: Claude` (or any Claude/Anthropic author/co-author trailer) to commits in this repo. Commits are always authored solely by the user.
- **i18n is mandatory.** This portfolio ships in three locales: `en`, `pt`, `es` — routed via `src/i18n/routing.ts`/`navigation.ts`/`request.ts` + `src/proxy.ts` middleware (next-intl), messages in `messages/{locale}.json` (statically imported in `src/i18n/messages.ts`, also reused by `request.ts` for server-side resolution). Routes live under `src/app/[locale]/`, giving each locale its own indexable URL (`/`, `/en`, `/es`) for SEO. Never hardcode user-facing text in a component — every string goes through `useTranslations`/`getTranslations`, and every key added to one locale file must be added to all three (`en.json`, `pt.json`, `es.json`) in the same change. The language switcher (`src/components/locale-switcher.tsx`) is a flag+name dropdown (desktop) / inline list (mobile, via the `size` prop) — no slide/pill indicator and no page-transition animation on locale change, the content just swaps.
- **Mobile-first and responsive.** Write base Tailwind classes for mobile first, then scale up with `sm:`/`md:`/`lg:`/`xl:` — never the other way around. Every new component or page must be checked at mobile, tablet, and desktop widths before being considered done.
- **Clean architecture / SOLID.** Keep components small and single-purpose — split a component the moment it takes on more than one responsibility (layout vs. logic vs. presentation). Avoid prop drilling: reach for composition (children/slots), context, or a store instead of threading props through more than one intermediate layer. One hook per file (`use-thing.ts`), one component per file. No giant "god" files — if a file is doing several unrelated things, split it.
- **npm major must match between dev and the Docker build.** `package-lock.json` is written by whatever npm runs locally, and a lock written by one npm major makes `npm ci` fail under another with a misleading `Missing: <pkg> from lock file` — the lock is fine, the tools disagree on transitive resolution. The `deps` stage therefore pins `npm@11` before `npm ci`. If you upgrade npm locally to a new major, bump that pin in the same change. To check a lock against the image's npm without Docker: `npx -y npm@<version> ci --dry-run`.
- **Database (Drizzle + Postgres).** Schema lives in `src/db/schema.ts`, client in `src/db/index.ts`. Route handlers stay thin (auth check + zod validation only) and delegate all business logic to `src/server/services/*`. Pages under `src/app/[locale]/projects/**` are `force-dynamic` — the Coolify build stage has no network access to the Postgres service, so these routes must never be statically prerendered. **Migrations run as a deploy hook, never in the build and never at container boot.** The build stage has no network access to Postgres, so a migration there cannot work at all. Putting one in `CMD`/entrypoint would re-run it on every restart and let a failed migration keep the container from starting. The supported path is Coolify's **pre-deployment command** — `node scripts/migrate.mjs` — which applies pending migrations before new code serves traffic, using `drizzle-orm`'s runtime migrator (`drizzle-kit` is a devDependency and is absent from the image). It exits non-zero on failure so the deploy stops instead of shipping code against a schema that never landed. Workflow when `src/db/schema.ts` changes:

1. `npm run db:generate` locally — commits the generated SQL under `src/db/migrations/`.
2. Commit and deploy. **Coolify's pre-deployment command applies it automatically**, so there is normally nothing else to do.

Fallbacks, when the hook is unavailable or you need to apply a migration without deploying:

- **No connection needed:** `npm run db:migrate:sql` writes `drizzle-migrate.sql`, a paste-ready script for the Postgres service's terminal. Each migration runs only if its hash is absent from Drizzle's journal, so pasting it twice is a no-op, and the journal it writes is compatible with the migrator — verified by applying via the script and then running a migration pass against the same database, which correctly did nothing.
- **With a connection:** open an SSH tunnel (`ssh -L 5433:<postgres-internal-host>:5432 <user>@<coolify-host>`) and run `DATABASE_URL="postgres://...@localhost:5433/<db>" npm run db:migrate`.

Only schema changes need this. Publishing releases or editing content goes through the API (`npm run release:publish`) and touches no migration.
